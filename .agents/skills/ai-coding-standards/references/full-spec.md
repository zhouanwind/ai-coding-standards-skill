# AI 编程规范 · 对话注入版

> 这是**一次性投喂**给 OpenHands（或任何 AI 编码工具）的版本。全文约 4300 字符，控制在注入预算内，日常编码只需关注 §1–§6。

---

## §1 十条铁律（任何情况下都不可违背）

1. **禁止伪造验证** —— 绝不声称跑过实际未跑的测试或命令。没跑就说没跑。
2. **禁止静默失败** —— 不得写空 `catch` / `except: pass` / 吞异常后静默返回默认值。捕获后要么正确处理，要么带上下文上抛。
3. **禁止硬编码密钥** —— Key / 密码 / Token /私钥走环境变量或密钥服务；示例写 `<YOUR_API_KEY>`；日志不打印敏感数据。
4. **最小必要改动** —— 只改任务需要的部分。不夹带重构、不顺手改格式、不重命名无关变量。发现范围外的问题**只报告，不动手**。
5. **先出计划再动手** —— 非平凡任务先给：改动文件清单（完整路径）+ 每处要点 + 复用的已有实现 + 风险与不确定点。
6. **验证后再交付** —— 交付前实际执行类型检查、相关测试、lint，并贴真实输出。失败要修因或说明阻塞，**禁止禁用检查让它变绿**。
7. **新增依赖需批准** —— 优先标准库 → 项目已有依赖 → 轻量新依赖。引入前说明为什么前面几级不够用。
8. **删除需批准** —— 不主动删文件或大段代码。列为「待删除」交人决定。
9. **不发明 API** —— 引用的库、函数签名、配置项必须真实存在。不确定就查证，不要猜，不确定处标注「待确认」。
10. **复用优先** —— 新增工具函数前先全库搜索。确无复用时说明原因。

## §2 工作循环（四步，不可跳步）

```
PLAN       先输出计划，暂不写代码
IMPLEMENT  严格按计划实现；计划有误 → 停下报告，不要自行扩大范围
VERIFY     实际执行验证命令（不是声称执行）
REPORT     固定四段式汇报
```

**REPORT 格式：**

```
【改动清单】文件路径 + 关键行 + 一句话说明
【实现理由】关联的需求或设计约束
【验证结果】实际执行的命令 + 真实输出
【风险与遗留】未覆盖边界 / 潜在副作用 / 建议后续动作
```

## §3 授权边界

| 级别 | 动作 | 处理 |
|---|---|---|
| L0 | 读文件、跑只读命令、跑测试/lint/类型检查 | 直接做 |
| L1 | 实现明确需求、修 bug、加测试、写注释文档、格式化 | 直接做，报告中列出 |
| L2 | 重构既有函数、调整目录结构、改公共接口签名、批量替换 | 先在计划里说明理由，再执行，逐项列出 |
| L3 | 引入/升级/删除依赖、改数据库 schema、动 CI/CD 与部署、删文件、变更对外 API 契约、触碰鉴权/支付/加密、**改版本号/打 tag/发 Release** | **必须先问，得到确认后再做** |
| L4 | 硬编码密钥、绕过测试与 lint、直接写生产环境、伪造验证结果、引入来路不明的依赖、**改写已发布版本的 CHANGELOG**、**强推分支或覆盖 tag** | **绝对禁止** |

## §4 代码基线

| # | 规则 |
|---|---|
| C1 | 语义化命名；禁止 `doIt`、`tmp`、`handleData` |
| C2 | 布尔量用 `is/has/can/should` 前缀 |
| C3 | 参数超过 4 个改用对象/结构体 |
| C4 | 单函数单职责，圈复杂度 ≤ 5，优先早返回而非深嵌套 |
| C5 | 魔法数字/字符串提为具名常量 |
| C6 | 只导入实际用到的符号 |
| C7 | 纯逻辑与 I/O（网络/DB/文件/时钟）分离 |
| C8 | 边界处显式处理空值，不假设非空 |
| C9 | 结构化日志，带 user_id / order_id / trace_id 等可检索标识 |
| C10 | 注释写「为什么」，不写「是什么」；不留注释掉的代码；临时方案带责任人与日期 |

**风格一致**：跟随项目现有命名、缩进、导入顺序、目录布局，不引入新风格。

## §5 错误处理、日志与测试

**错误处理**
- 捕获前先决定：**处理它，还是带上下文上抛它**。没有第三种选择。
- 不用 `except Exception` 宽泛捕获后重新包装成无信息量的通用错误。
- 重新抛出时补充上下文：哪个操作、哪个输入、什么后果。
- 用户可见文案与排障信息分层；区分「没有结果」与「出错了」。
- 资源确定性释放：`with` / `try-finally` / 上下文管理器。

**日志**
- 分级：ERROR 需人工介入｜WARN 异常但自愈｜INFO 关键业务节点｜DEBUG 排障细节。
- 参数化写法（`logger.info("x %s", x)`），不用 f-string 拼接。生产路径禁止 `print` / `console.log`。

**测试**
- 每个 Bug 修复必须配回归测试，且该测试在修复前必须失败。
- 测行为，不断言实现：断言对外可见的结果（返回值、异常类型与消息、副作用、状态变化）。
- 必测边界：空集合、单元素、超长输入、零与负数、Unicode、并发、超时。
- 必测异常路径：不只测成功，也测失败时的错误类型与信息。
- 禁止空断言、禁止 `assert True`、禁止 mock 掉被测逻辑本身、禁止放宽既有断言。
- 测试名描述行为：`test_returns_empty_when_user_has_no_orders()`。
- 覆盖率参考：核心逻辑 ≥ 80%，工具层 ≥ 60%。**覆盖率不等于信心，断言对了才是信心。**

## §6 安全红线（绝对禁止）

1. 硬编码密钥、密码、Token、私钥
2. SQL 字符串拼接（必须参数化）
3. 关闭证书校验（`verify=False`、`InsecureSkipVerify`）
4. 在生产数据上执行迁移或破坏性操作
5. 伪造或篡改测试结果
6. 用 `any` / `# type: ignore` / `@ts-ignore` / `eslint-disable` / `# noqa` 掩盖真实的类型或 lint 问题
7. 把用户隐私数据发往未授权的第三方服务
8. 引入来源不明的依赖（无仓库、非官方镜像、近期更新的可疑包）

**其他**
- 文档与注释：注释解释**为什么**；临时方案标注责任人与期限；新增公共 API 写 docstring/JSDoc（参数、返回、异常、示例）；架构变更写 ADR。
- 性能：没有 profile 数据支撑的「优化」不要做；区分「必须优化的热路径」与「想当然的优化」；性能改动给出前后量级对比，没测就说明没测。
- 提问：给**具体选项 + 你的倾向 + 理由**。❌「您希望我怎么做？」 ✅「A 和 B 都有 sync()，我倾向 A，因为它已处理缓存失效，确认后我按此实现。」

## §7 发版与打包（仅在发版任务时适用）

> 日常编码任务**不需要**阅读本节。完整规则见 `AI编程规范-发布打包详解.md`。

**版本号增长规则**

| 变更类型 | 增长位 | 示例 |
|---|---|---|
| 界面美化、bug 修复 | 三级 PATCH | `v1.0.0` → `v1.0.1` |
| 功能增加 | 二级 MINOR | `v1.0.0` → `v1.1.0` |
| 软件重构、重大功能调整 | 一级 MAJOR | `v1.0.0` → `v2.0.0` |

- 一次发布含多种变更时**取最高位**。
- **每次上传 GitHub，版本号必须严格大于上一个已发布版本**；禁复用版本号、禁覆盖 tag。
- 版本号单一来源（`package.json` / `pyproject.toml` / `VERSION`），禁止多处各写一份。
- CHANGELOG 只追加到 `[Unreleased]`，不改写已发布段落。

**发布顺序（不可颠倒）**

```
aarch64（AI 开发沙箱，权威架构）：完整测试 → 构建离线包 → 安装冒烟
   ↓ 不通过则停止，不做 x86_64
x86_64：独立下载依赖 → 构建离线包 → 安装冒烟
   ↓
更新 CHANGELOG 与版本说明 → 提交 → 打 tag → 推送 GitHub → 创建 Release
```

**离线包要求**：自带运行时与依赖（用户无需预装任何运行环境，数据库除外）；一键 `install.sh`；带 `SHA256SUMS`；架构自检不匹配则拒绝安装；**禁止安装时联网下载依赖**。

**依赖必须按架构分别下载**——同类库不同架构编译了不同的二进制扩展（numpy/lxml/cryptography），禁止跨架构复用。

**Release Notes 必须同时给出两个架构的下载链接与 SHA256**，缺一不可。

## §8 交付前自检

任一不满足 → **不得宣布完成**，需说明卡在哪一项：

```
[ ] 类型检查 / 编译通过
[ ] 相关单元测试通过（含新增测试）
[ ] Lint / Format 通过
[ ] 无静默异常吞噬
[ ] 无硬编码密钥与敏感信息
[ ] 新增/修改的公共接口有完整文档
[ ] 改动范围与需求一致，未夹带无关重构
[ ] 已复用项目已有实现，未重复造轮子
[ ] 引用的 API 确认存在
[ ] 报告四段式完整（改动/理由/验证/风险）
[ ] CHANGELOG 的 [Unreleased] 段已追加本次变更
[ ] 提交信息符合 <type>(<scope>): <subject>
[ ] 未触碰版本号、tag、发布动作（属 L3，需先确认）
```
